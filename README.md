課題: Excel上のデータは「名称」であることが多いですが、ServiceNow内部は sys_id で管理されています。

懸念点: Field Map の Referenced value field name（例：name）を正しく設定していないと、システムは名称を sys_id と誤認して検索し、紐付けに失敗します。

対策: Excelの値がB表のどのフィールド（名称、コードなど）と一致するかを事前に定義し、マッピング設定を徹底する必要があります。

課題: 標準設定（Choice Action = create）では、参照先が見つからない場合に新しいレコードを作成します。

懸念点: Excel側の入力ミス（例：「総務部」を「総務ブ」と誤記）があった場合、B表に誤ったマスターデータが自動作成され、データ汚染が発生します。

対策: 原則として Choice Action = reject に設定し、不整合なデータはインポートさせない「ガード」が必要です。

3. 大文字・小文字、および前後の空白による影響
課題: データベース検索は形式に厳密です。

懸念点: Excel内の不要な空白（"Apple "）や、大文字小文字の差異（"google" と "Google"）により、同一データと見なされず紐付けに失敗する可能性があります。

対策: Field Map で「Case sensitive」のチェックを外す、またはインポート前にデータのクリーニング（トリミング）を実施する運用が必要です。

4. 複合主キー（Coalesce）の整合性への影響
課題: 参照フィールドが複合主キーの一部である場合、その成否が重要になります。

懸念点: 紐付けに失敗し、かつ Choice Action = ignore の場合、フィールドが空（Null）のまま登録されます。これにより、後続のインポートで主キーの重複検知が正しく機能せず、データが重複するリスクがあります。

対策: 主キーを構成する参照フィールドについては、紐付け失敗＝インポート失敗（reject）とする厳格な設定が推奨されます。


1. 唯一の識別子（Coalesce）の特定
懸念点: A表側の一意な項目（主キー）が不明な状態では、Excelデータが「新規作成」なのか「既存更新」なのか判断できません。

リスク: * データ重複: Coalesce設定がない場合、すべて新規レコードとして登録され、本番データが二重になります。

3. データ形式と型の不一致
懸念点: Excel側の入力形式（日付、選択肢、数値）が、ServiceNow側の定義（強データ型）と一致しない可能性があります。

リスク: 選択肢に無い値がExcelから入ることで、選択肢リストが汚染されたり、インポートエラーが発生します。

課題: Transform Map Script を活用し、Excelの表示値をServiceNow内部値に変換するロジックの実装が必要です。

### 【中文版】ServiceNow 列表画面 (List View) 搜索调优调查报告

**1. 调查对象**

* **功能范围：** 传统后端管理界面的列表视图 (Backend List View)
* **搜索引擎：** Zing Text Search (ServiceNow 的基础文本检索引擎)

**2. 概要**
列表画面的主要设计目的是“精确的数据管理和排序”。因此，其搜索调优能力与全局搜索（Global Search）不同，主要集中在**“文本搜索 (Search for Text)”模式下的字段优先级控制**和**索引降噪**。

**3. 可实现的调优手段 (具体配置)**

针对本项目中的数据表，在列表画面能实现的调优仅限于以下两点：

* **A. 字段权重配置 (Field Weights / ts_weight)**
* **适用场景：** 仅当用户在列表顶部的搜索下拉框选择 **“for Text (文本)”** 进行搜索时生效。
* **配置方式：** 在数据字典 (Dictionary) 中，为特定字段（如 ID、姓名）添加属性 `ts_weight`。
* **效果：**
* 设定 `ts_weight=50` 的字段（如员工ID），其匹配结果会排在 `ts_weight=1` 的字段（如备注）之前。


* **局限性：** 如果用户使用“列头过滤器 (Column Filter)”或按特定列排序，此权重失效。


* **B. 索引排除 (Index Exclusion / no_text_index)**
* **适用场景：** 所有文本搜索场景。
* **配置方式：** 在数据字典中，为不需要搜索的字段（如创建时间、系统日志）添加属性 `no_text_index=true`。
* **效果：**
* **降噪：** 防止用户搜索关键词时，匹配到无关字段（如日志）中的内容，提高结果纯度。
* **性能：** 减少索引体积，微幅提升搜索响应速度。





**4. 无法实现的功能 (技术限制)**
在列表画面中，以下功能**不支持**（仅在全局搜索支持）：

* ❌ **同义词 (Synonyms)：** 搜“手机”无法匹配“Mobile”。
* ❌ **拼写纠错 (Typo Handling)：** 搜“Laptap”无法匹配“Laptop”。
* ❌ **强制置顶规则 (Result Improvement)：** 无法强制将特定记录固定在列表顶部，列表必须遵循严格的排序（Order By）逻辑。

**5. 结论**
对于列表画面，最佳的优化策略是：**为核心字段（ID、名称）配置高权重，并从索引中排除非业务字段**。这可以确保管理员在使用文本搜索时，能够优先获得高相关性的结果。
